# Milestone 3: independent rules engine

Status: core rules baseline implemented and ready for Milestone 4 creator integration. Original parity/preservation criteria have source-derived synthetic coverage (139 project tests passed at the latest code verification); complete Android runtime and upstream-mechanic parity are not claimed.

Scope review: this document contains chronological implementation notes, so older statements about future work and test counts describe their implementation stage. The next priority is a working create/save/reopen/edit flow. Viewer/storage integration and completion of editable document fields belong to Milestone 4. Additional automatic handlers should follow concrete creation blockers, with visible diagnostics and an explicit manual workflow for unsupported mechanics; full upstream automation is not a prerequisite for the creator.

## Reading the code

Start with `character-document.ts` for saved inputs, generated instances and play state. Then read `character-preview.ts`, which combines species, abilities, proficiencies, class rules and stats into a detached proposal. `class-preview.ts` handles mandatory features, optional selections and their dependencies, followed by levels and spells. Individual `*-rules.ts` handlers validate and derive one part of that proposal. `document-operations.ts` adds document validation, snapshot/history preservation and explicit acceptance; `session-rules.ts` and `casting-rules.ts` perform play actions separately from recalculation.

A **grant** records why a selected definition belongs to the character; an **instance** holds its stable identity, snapshot and user customization. Multiple grants can support one instance. A **contribution** records an origin-tagged value such as a proficiency or species bonus. A **preview** proposes a change without saving it; diagnostics block invalid proposals, while adjustments request a decision about existing HP or resource usage. `canAccept` in the complete preview therefore means more than a calculation succeeding.

`src/app/rules/level-rules.ts` has no Angular, database or network dependencies. `deriveLevelRules` accepts explicit ordered class inputs, automation flags, manual HP/resources and play state. It returns proposed totals, pool definitions, provenance and adjustment diagnostics without mutating or saving anything. Creator UI, content-to-class input adaptation and the authoritative character document remain separate upcoming work.

Implemented: Android average HP calculation with full first die only for the first selected class, Constitution modifier, total level/proficiency bonus, merged generated hit-dice pools, regular caster contributions/slot tables, separate pact pools, manual pools and nullable HP overrides. The `android-v1` policy preserves the observed level-2 pact table with a warning; it is not a claim of official edition correctness. Half/third contributions use floor and artificer uses ceiling according to the Android baseline.

Generated resource IDs are stable tuples independent of display labels. Existing counters and annotations survive recalculation; new counters start unused. Removing a pool retains its session state and reports an adjustment when previous pool definitions are supplied. Usage above a reduced total and HP above a reduced maximum are reported, never clamped. The later editor must explicitly resolve adjustments before applying a preview.

Executable parity coverage: B01-B03 and B06-B08, plus repeat application, level increase/decrease, preservation, disabled HP/hit-dice automation, manual pools, zero overrides and invalid-input rejection. All 64 project tests pass after this first implementation slice. No Android runtime capture was used.

`feature-rules.ts` resolves explicit class/subclass keys against a supplied pinned in-memory content index, produces class inputs for level arithmetic, and selects qualified features up to the chosen class level. Preview instances carry embedded snapshots, source/revision binding, stable grant IDs and preserved customization. Generated IDs are deterministic initial identities; previously assigned IDs are retained. Manual instances can coalesce with matching generated features; suppression targets individual stable grants. Features from other content sources are retained by this source-scoped operation.

Level decreases and subclass replacement list obsolete instances rather than silently deleting them. Errors return the existing instances unchanged with `canAccept: false`. A changed content revision requires a separate explicit update preview; class/subclass casting conflicts and unsupported progressions require handlers rather than guessed totals. Full content identities distinguish equal feature names at different levels/classes/publications. Snapshots and customization are detached from input objects.

Feature tests cover B04/B05, W01/W02/W05, repeat application, qualified multiclass features, subclass ancestry/replacement, level reduction, manual additions, suppression, source isolation, duplicate references, missing definitions and explicit-update blocking. These are source-derived synthetic fixtures, not captured Android runtime output.

`spell-rules.ts` previews `additionalSpells` from explicit eligible owners (class/subclass/feature/species/feat records). Fixed innate/known/prepared grants are distinct from expanded-list availability. Numeric character-level requirements and `sN` spell-level requirements are gated by explicit inputs. Spell UIDs resolve exact publications, default PHB, and strip casting suffixes for lookup. No Android name-only fallback is used.

Explicit `choose.from` and supported filter `choose` selectors produce stable choices and validate supplied candidate keys/counts. `all` selectors grant all matching spells or expand availability without selecting spells. Multiple additional-spell blocks and selectable casting abilities require explicit input. Unsupported filters/frequencies/structures fail visibly. This is a supported subset, not complete corpus-wide spell automation.

Casting source identity includes source, selection, owner and block. Spell instances additionally distinguish list and innate usage definition; grants can coalesce within the same source/list without sharing counters across different sources. Snapshots, previously assigned IDs and customization survive repeats. Suppressing one of several grants retains the others; manually retained spells survive loss of all grants. Frequency/count/resource metadata is preserved in grants, but converting innate usage into resource pools and casting operations remains future work. Explicit content-update previews are still required for revision changes.

Spell tests cover level gates, expanded availability, explicit choices, unresolved filters, block/ability selection, source separation, innate usage distinctions, suppression/shared grants, manual preservation, level decrease, retained notes/counters, detached state and publication isolation.

`spell-filters.ts` implements the audited pipe-separated conjunctions with semicolon alternatives for level, class, school, publication, spell attack and ritual. Matching is case-insensitive; primary and variant class memberships from imported spell data are supported. Empty filters select all spells in the supplied index. Unknown fields, advanced operators/ranges, invalid values and excessive expression sizes are rejected. The index defines the available corpus; callers can restrict it to enabled publications. `inspect-spell-selectors.mjs` inventories/validates query syntax from pinned class, race, feat and optional-feature data without saving the corpus; this verifies syntax coverage, not upstream renderer parity for every matching result.

`previewClassRules` composes feature, level and spell previews. It builds owners from selected classes/subclasses and eligible unsuppressed feature grants, inherits explicit class casting ability where available and accepts per-owner block/ability/spell-level options. Combined multiclass slots are deliberately not used to infer class-specific spell-level eligibility. A required selection/reference failure retains previous feature/spell/pool state in the combined proposal. Resource/HP adjustment diagnostics still require explicit resolution by the future acceptance layer. No preview automatically saves, clamps or updates content.

Validation after composition/filter support: all 84 project tests pass; the pinned selector inventory contains 158 unique expressions, all accepted by the parser. Matching behavior is covered by synthetic tests, including multiple clauses, alternative values, variant class membership and rituals. Production build succeeds with the existing initial-size warning.

`optional-feature-rules.ts` validates choice slots, unique selections and feature types, producing stable grants/instances with coalescing, manual preservation and suppression. `optional-progression.ts` derives cumulative counts from level arrays and sparse level breakpoints on selected classes/subclasses. Stable slot IDs retain selections across level changes; decreases require fitting the new count. Unknown progression metadata/forms block acceptance. `prerequisites.ts` handles total/class-qualified levels, exact spell/optional-feature requirements and explicit pact facts, with OR alternatives and AND conditions. Item descriptions, narrative requirements and filter-based prerequisite spells remain blocked. The composed class preview derives prerequisite class levels from actual selections; additional prerequisite facts must be supplied from eligible character selections, without assuming cyclic dependencies are satisfied.

`species-rules.ts` previews materialized species snapshots and a contribution ledger for normalized movement, conditional movement details, resistances/immunities/vulnerabilities, condition immunities, senses, size and creature types. Manual contributions remain separate and untouched when generated species contributions change. Repeating a selection retains its instance/customization; replacement/removal reports the old instance for explicit acceptance. Unsupported forms and revision changes block acceptance. This ledger does not merge movement into a single effective speed or decide equipment/conditional eligibility. Ability bonuses and proficiency choices still require their own handlers.

Optional progression and selected optional-feature spells now participate in the composed class preview. Unresolved slots/prerequisites prevent a partial update. Species previews remain separate; full document orchestration still needs to combine species, proficiencies, stats and class previews atomically.

`proficiency-rules.ts` extracts supported starting-class saving throws/proficiencies and later-class multiclass gains, plus species proficiency fields. Fixed contributions and explicit `choose.from` pools retain origin and manual ledgers. Missing selections, general `any...` pools and unsupported structures block acceptance. Contributions are regenerated independently, so manual proficiency values are never overwritten or merged into generated origins. General pool expansion, expertise-choice handlers and descriptive proficiency parsing remain extensions.

`derived-stats.ts` computes six ability modifiers, proficiency bonus, eighteen skills, saves, initiative and Android-policy AC from validated inputs. Multiple proficiency contributions use the greatest rank rather than stacking; explicit half proficiency is floored and expertise doubles PB. Miscellaneous bonuses and nullable zero overrides are preserved. Eligible equipment is filtered by equipped/attuned state; medium armor caps only positive Dexterity at 2, heavy armor omits Dexterity, and the best shield plus miscellaneous bonuses apply. The Android best-AC/unarmored comparison policy is retained rather than claiming full equipment legality. Jack-of-all-trades is not inferred; half-proficiency contributions must be explicit until its feature handler exists.

Validation: all 96 tests pass; production build succeeds with the existing initial-size warning. New fixtures cover cumulative progressions, prerequisite identity/alternatives, integrated optional choices/spells, starting vs multiclass proficiencies, manual expertise/half ranks, zero overrides, equipment eligibility and B14/B15 AC baselines. `inspect-rule-shapes.mjs` reports pinned optional prerequisite/progression structures without saving descriptions or a corpus. No Android runtime capture was used.

`session-rules.ts` provides pure explicit damage/heal/temp-HP/death-save/resource-use/override operations and versioned rest policies. Android policy restores half of each hit-dice pool (minimum one), retains temporary HP, clears all spell-slot use on long rest and fully restores SHORT_REST_ONE on long rest. `web-viewer-v1` preserves the current viewer's all-dice/temp-clear/rest-condition behavior, including recovery of only one SHORT_REST_ONE use. Feature MANUAL pools and undefined/orphan pools are preserved. Zero HP overrides are an intentional web correction to Android's minimum-one edit. Derivation never invokes a healing/rest/override action implicitly.

`character-preview.ts` composes class/optional/spell, species, proficiency and derived-stat previews. Constitution has one authoritative ability input. Eligible species spell owners join class spells, and health/session fields are validated and retained. Invalid components produce no combined proposal. HP/resource shrink adjustments retain existing counters and block acceptance pending an explicit decision. Removal lists retain obsolete instance snapshots/customization for review. This is a pure orchestration input/result, not yet the portable versioned character document or repository schema.

Validation after session/orchestration work: all 102 tests pass, including B09-B13 health/rest baselines, explicit policy differences, preserved annotations/counters, combined species spell/proficiency output, repeat derivation, blocked partial updates and HP/usage shrink conflicts. The existing RestService/viewer remain unchanged until native document integration.

`character-document.ts` implements bounded portable-JSON native validation/round-trip for supported rule inputs, pinned bindings, selected snapshots, instances, active links, derived numeric values and session state. Unknown schema/rules versions are rejected, along with malformed values, runtime Sets/nonportable values, duplicate IDs and over-limit documents (10 MiB, depth 64, 250,000 nodes). Root, identity, compatibility and extension fields are preserved. Supported scalar and resource/source overrides use known targets; no arbitrary imported property path is applied. The application character ID is a UUID; engine instance IDs remain stable opaque strings and retain previously assigned IDs.

`document-operations.ts` provides pinned-source `previewDocument`, guarded `acceptDocumentPreview` and document play actions. Preview stores a private plan, checks the complete canonical base document for staleness, and ignores edits to the public review copy. Acceptance requires an explicit keep/clamp choice for excess HP/usage and retain/discard for removed resource state. It never saves or advances server metadata. Selected snapshots/dependencies are bounded to 1,000 records, so rendering/play actions can use the accepted document without a compendium cache. Removed instances retain customization/snapshots in compatibility history; eligible generated features/spells/sources and species can restore their earlier identity/customization when selected again. Unknown future schema versions are not migrated automatically.

`resource-action-rules.ts` materializes supported innate daily/rest uses, distinguishing shared list pools and each-spell pools, and accepts manual resources. It preserves casting labels/customization and typed ability/DC/to-hit/spellbook/resource-total overrides, including zero values. Manual action text/order/customization survive derivation; action links to removed/missing instances, sources or pools block acceptance until explicitly edited. Unsupported casts/resource frequency structures block rather than inventing counters. Multiple-source derivation and cyclic/generated prerequisite proof still require handlers; native prerequisite facts currently come from manual saved selections/pacts. Empty enabled-publication lists mean all publications in the supplied pinned index.

Validation after this stretch: 111 tests pass before the final ledger persistence update, covering native round-trips, unknown versions, stale/forged previews, review-copy mutation, explicit adjustment decisions, casting/resource customization, dangling links, play policies, history restoration and shared/per-spell innate uses. Native documents are not yet integrated into the viewer, storage repository, Android projection or creator. Item/monster instance models and broader audited-field coverage remain to be implemented before declaring the full migration document contract complete.

`ability-rules.ts` separates explicit base/manual scores from opt-in species contributions. It handles fixed bonuses/penalties and explicit `choose.from` count/amount allocations, including default count/amount of one. Multiple alternatives require an index; repeated/invalid/ineligible allocations block acceptance. Weighted or unknown forms fail visibly. Effective Constitution flows into HP and all effective scores flow into stats/casting; repeated application or species replacement never rewrites/accumulates base scores. Values outside the supported 1–30 range produce diagnostics rather than clamping. `applySpeciesAbilities` defaults off so existing/legacy effective scores are preserved until explicitly configured.

Native creation stores the ability preference/choice, and derived state stores effective scores and origin-tagged contributions. All 115 tests pass after this integration, including repeat application, alternative allocation, penalties and replacement. The pinned species metadata inspection is available through `inspect-rule-shapes.mjs --abilities`; it is structural source evidence rather than an Android runtime capture.

`previewContentUpdate` explicitly compares selected snapshots and creation/choice roots with a proposed same-source revision. It reports changed fields/links and missing identities, refreshes eligible snapshots only in a detached candidate, reruns all supported rules and preserves instance IDs, source labels, overrides and usage. Missing/renamed required identities require explicit selection editing; it never searches by name or guesses aliases. Dependencies no longer required by the new graph can be removed on acceptance. Former definitions/bindings remain in bounded compatibility history; historical-instance snapshots are refreshed only when uniquely present at the new revision.

Content-update results use the same private acceptance plan and full-base staleness check. HP/slot/usage reductions require decisions, and other characters/current documents remain unchanged until acceptance. Cross-source replacement, automatic rename mapping and multi-source derivation are not supported. The target binding must match the supplied source/revision; repository integration must supply authentic commit/adapter metadata. Current API expects a complete supported in-memory index, not only selected snapshots, when filters are evaluated. User-facing update controls remain Milestone 4.

Validation: all 118 tests pass after explicit update support, including changed snapshots, retained customization/usage, missing content, source mismatch, stale update acceptance and slot-reduction decisions. Build succeeds with the existing initial-size warning.

General proficiency pools now expose validated choices. `any`/`anySkill` use the eighteen supported skills; language/tool/general catalogs must be explicit versioned creation inputs rather than inferred from descriptions. Fixed grants from the same origin are excluded from that origin's choices, independent of object-field order. Language `other` is treated as a choice requiring a catalog, not a literal language. Exact item tags resolve to publication-qualified cached item/base-item keys. Descriptive tool choices, missing publications and ambiguous multiple proficiency packages block instead of silently unioning alternatives or granting descriptive text as a proficiency.

`applyProficiencies: false` explicitly switches to manual contributions only; the default remains automatic. This preference is persisted and validated in native creation. Manual expertise and bonuses survive either mode. Language/tool catalog acquisition, package/merge semantics and natural-language tool-choice handlers remain future work. `inspect-rule-shapes.mjs --proficiencies` inventories the pinned raw shapes without saving content.

Named-resource innate spells now require explicit `creation.resourceBindings` connecting a casting-source ID and upstream resource token to an existing feature-use pool ID. The engine does not guess a Ki pool from a display name or invent its total. Supported daily/rest and named-resource grants produce validated spell-cost definitions with exact spell/grant/pool links. Creation bindings and derived costs round-trip in native documents. Unknown costs, duplicate bindings and missing pool/source targets block acceptance.

`spend` and `recover` session actions operate on detached state. Spending rejects insufficient capacity, including previously retained over-total usage; recovery never goes below zero. `performSpellResourceUse` consumes the accepted cost definition rather than editable labels. These are explicit play actions, not retry-idempotent sync commands; outbox operation IDs remain Milestone 6. Slot selection for ordinary casting and special casts/charges handlers still need implementation.

All 125 tests pass after named-resource/cost operations. Fixtures cover shared Ki-style costs, missing/duplicate bindings, innate use exhaustion, rest recovery, positive-amount validation and unchanged original/annotation state. The pinned `--innate` structural inspection found daily/rest/will/ritual/resource forms and named Ki costs in class/species/feat/optional-feature inputs; no casts wrapper was observed in that inspected subset.

`casting-rules.ts` adds explicit native-document casting operations. Ordinary casting requires a prepared spell or a configured known-spell source and an explicitly selected spell-slot pool at or above the spell level. Spending is atomic, rejects exhausted pools and reports the selected rank for upcasting. Eligible cantrips, explicit at-will grants and supported ritual capabilities do not spend slots. Limited innate spells require their accepted resource cost; a cantrip's level alone cannot bypass that restriction. Casting-source preparation and ritual capabilities are validated, persisted and configurable through source overrides.

Casting validation covers eligibility and resource spending, not spell effects, concentration, casting time, components or equipment restrictions. Additional ritual policies (such as casting unprepared spellbook rituals) and special casts/charges require their own handlers. Native documents now require spell-slot pool ranks in the range 1–9.

All 128 tests pass after ordinary casting support. New fixtures cover explicit pool selection, upcasting, exhaustion, incorrect/under-level pools, known-source configuration, ritual capability, cantrips and preserved original state/annotations. The production build succeeds with the existing initial-size warning.

Multiple object packages in skill/language/tool proficiency arrays now expose an explicit `packages` choice. Each package has a detached data preview and a stable answer ID; `creation.proficiencyAnswers` stores exactly one option value (the zero-based index as a string). Only the selected package is parsed. Fixed grants and nested choices retain their existing validation, and nested answer IDs include the package index so switching packages cannot reuse a different package's choice. Package indices are scoped to the pinned content revision; explicit content-update review is still required when definitions change. No automatic union or ambiguous merge semantics are inferred.

The composed character preview blocks acceptance until package and nested selections are complete. Switching packages regenerates their contributions while preserving manual expertise and session state. Manual-only proficiency mode exposes no packages. All 131 tests pass, including invalid/multiple package answers, detached option previews, nested-choice isolation and full-preview switching. Production build succeeds with the existing initial-size warning. Descriptive tool choices and proficiency merge/expertise automation remain extension work.

Ability-score prerequisites now support an array of alternative threshold objects, with all score thresholds inside an object required together. Only the six supported abilities and integer thresholds 1–30 are accepted; missing scores and malformed/unknown requirements cannot pass. Standalone class previews accept explicit score context. Whole-character previews always supply effective ability scores, including enabled species contributions, overriding conflicting supplemental prerequisite scores. Disabling or removing those contributions reevaluates eligibility without rewriting base scores.

All 134 tests pass after ability prerequisite support, covering alternatives, combined requirements, missing scores, invalid shapes and composed optional-feature eligibility with species bonuses. These are synthetic handler fixtures, not a corpus-wide prerequisite audit. Narrative/item prerequisites and other unhandled forms remain blocked.

Optional spell prerequisites now also use independently derived current class/subclass/class-feature and supplied species spell grants. These grants are evaluated before optional selections; their explicit spell choices and suppressions apply. Expanded-list availability does not count as possessing a spell. Losing a required grant through level reduction or suppression blocks the combined proposal and preserves previous state. Saved optional-feature spell grants are not reused to let an option satisfy its own prerequisite. Independent spell-preview failures also block final acceptance.

Manual prerequisite facts remain explicit inputs. Dependencies between optional features, including spells granted by another optional selection, still require a dependency-resolution handler; this change does not assume cyclic selections are valid. All 136 tests pass, including current class/feature grants, suppression, level reduction, expanded-list exclusion and self-grant rejection. Production build succeeds with the existing initial-size warning.

Optional-selection dependencies now resolve in bounded passes. Each selection must first pass the existing slot/type/revision/prerequisite checks; only its active, unsuppressed grant adds an optional-feature fact. Spells from eligible options then join the prerequisite context through the normal spell handler, including explicit choices and suppression. Passes continue while eligibility grows, independent of answer order. Unresolved dependencies block the final proposal; previous generated instances cannot seed an otherwise unsupported cycle or self-grant. Explicit manual prerequisite facts remain valid seeds. Resolution is capped at 512 selections, and spell failures or limit violations block acceptance atomically.

All 139 tests pass, including an optional-feature chain with a spell prerequisite, answer reordering, repeated derivation, unseeded cycles with previous generated state, and suppressed dependency roots. Production build succeeds with the existing initial-size warning. Unsupported prerequisite forms still require handlers; dependency resolution does not interpret narrative requirements.
